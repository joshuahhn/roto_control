## Semantics and capability sources

- Layout ownership describes COMP-owned versus user-owned Custom configuration. Focus link, parameter destination, COMP path/name and a Device named CUSTOM do not establish ownership. The deployed .45 v3 lacks owner/category metadata: display Legacy / unclassified. The separate #9 source branch adds explicit categories but has not been integrated or deployed here. Do not advertise existing records as COMP-owned or Custom by inference.
- Each Mapping Layout contains Track → Device (protocol Plugin) → control pages. DEVICE first, then LAYOUT | TRACK is reading order. FUNC selects Tracks; SEL selects Devices in the routing Track. Control pages are neither outer Layouts nor list banks.
- Management targets stable Browsed IDs and their real parents. Viewing, committed Routing and hardware selected/pending fields remain separate. LOCK divergence must never be combined into a fabricated activation triple.
- Retain .45 Browse → explicit Activate and LIVE behavior. LIVE follows local routing even offline; it does not establish transport/ACK readiness or turn on Follow. Activate remains guarded, with no hardware=True escape hatch.
- Put ownership availability and explicit disabled reasons in the shared command capability projection. UI must not inspect names to derive policy. Reuse Details for complete Viewing/Routing/ownership information and selected/pending differences; do not make the compact main window taller merely to expose every diagnostic.

## Source audit of existing v3 commands

The implementation authority is code/py/roto_python/layouts.py and promoted RotoPythonExt methods, not a view-owned copy of the registry.

- CreateLayout/CreateTrack/CreatePlugin create empty descendants and retain current routing. Creating a Track/Device in the routing parent may announce an updated candidate list; that is not a routing switch. Methods call existing guard/capture/save/menu behavior. Device/Track names use the protocol12-byte printable ASCII rule; Layout uses its separate nonempty-string rule.
- RenameLayout has no hardware-idle guard. RenameTrack/RenamePlugin check LEARN, but have different behavior for active versus inactive records. Inspector must add an explicit management capability policy before calling them; do not presume identical protection across methods.
- RenamePlugin sets name_mode=manual. A Device following its linked COMP name therefore cannot expose ordinary Rename as an implicit opt-out. Offer a separate Use manual name draft action and disclose that change. It must preserve Focus link and must not rename the TD COMP.
- Active Track/Device renaming passes through SetLayoutNames, which publishes display names and captures the active library. Names do not constitute mapping identities. Registry/runtime display state may change even though target IDs, hashes, Values, mapping configuration and readiness remain. Tests compare canonical persistent mapping fields, not a frozen diagnostic Label string.
- RemoveLayout/RemoveTrack/RemovePlugin enforce last-item guards and choose the first remaining sibling as successor. Deleting an inactive parent may update that parent's saved active-child pointer without changing actual routing. A confirmation must show the exact successor the existing method will use; do not promise arbitrary successor selection without extending and testing the manager contract.
- Existing manager methods may mutate in-memory data before save/announce fails. Treat arbitrary callbacks and transport failures as possible partial results, refresh authoritative state, and report what actually changed. Do not claim a global transaction or silently replay the intent.

## Shared module interface

Keep management rules once under base_commands, backed by the TDControllerAdapter. Fold/Popup retain only their local form, detached snapshots and drafts. No new controller, second registry, per-frame tree scans or permanent watcher.

Proposed interface (not installed):

- Management(context): detached records for Layout/Track/Device, full parent IDs, display policy, explicit ownership state and action capabilities. Returns a management revision plus model/session and observed routing tokens.
- Manage(intent, action, payload): freshly validate intent and call exactly one promoted registry command for Create/Rename/manual-name. Return actual record IDs/context and result/error. Create returns a new browsable empty context; activation is independent.
- PrepareDelete(intent): derive descendant scope/library counts, classification, exact successor context and immutable confirmation fingerprint. It performs no writes.
- Delete(confirmation): revalidate the full scope, session, routing and registry revision before existing removal. Return removed/remaining IDs and actual routing/error, including partial completion.

Management revision must cover structural IDs/order/parents, display name/policy, owner metadata and saved active-child pointers. Delete confirmation also covers affected registrations/control-page libraries and successor. Do not reuse a live Value fingerprint: controller Value traffic alone must not invalidate a name draft. Library assignments, owner/link policy, concurrent rename/reorder/removal or changed routing/session must invalidate affected intent. Build the bounded snapshot only on opening/explicit refresh and before commands, not on each CC. No OP/Par/process handles in saved drafts or TD storage.
